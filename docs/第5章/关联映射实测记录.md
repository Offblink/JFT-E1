## 一、两套实现的 SQL 条数（日志实测）

| 场景 | XML 方式（嵌套结果） | 注解方式（嵌套 select） |
|---|---|---|
| 一对一（查 1 个员工 + 部门） | **1 条**（一条 LEFT JOIN） | **2 条**（1 主 + 1 子查询） |
| 多对一（查 4 个员工 + 各自部门） | **1 条** | **4 条**（1 主 + 3 子查询，见下） |
| 一对多（查 1 个部门 + 员工列表） | **1 条** | **2 条**（1 主 + 1 子查询） |
| 多对多（查 1 个员工 + 技能） | **1 条**（两次 JOIN 穿中间表） | **2 条**（1 主 + 1 子查询） |

⚠️ **多对一注解版实际是 1+3 而不是 1+4**：4 个员工里张伟与李娜同部门（dept_id=10），第二条子查询的
`statement + params` 命中 SqlSession **一级缓存**被复用，日志里只出现 3 次 `findById`。
数 SQL 条数要按日志实际行数点，不能机械按 1+N 算。

## 二、三处与讲义/老师代码不一致的实测结论

1. **"LEFT JOIN 无关联会产生全 null 的技能对象"在 MyBatis 3.5.x 不成立**：赵敏在中间表里没有任何关系，
   `many2manyByXml(4)` 的 SQL 仍返回 1 行（日志 `Total: 1`，skill 侧整行全 null），但映射层判断嵌套
   resultMap 各列全 null 就跳过该元素 → `Emp.skills` 是**空集合 `[]`**。真实代价只是白查了一行的带宽，
   而不是集合里多一个脏对象。用例里留了 `assertNotNull(s.getId())` 当版本哨兵。

2. **`DISTINCT` 在本项目这条多对多 SQL 里一条行都去不掉**：中间表主键是 `(emp_id, skill_id)`，
   不可能出现完全重复的关系行；真正把 N 行归并成"1 个员工 + N 个技能"的是 `<id property="empId">`。
   （老师的写法保留，注释里写明分工。）

3. **老师注解版的两条 SQL 白查了一次 JOIN**：`one2oneByAnn` / `many2oneByAnn` 既写了 `LEFT JOIN dept`
   并查 `d.deptno AS d_deptno`，映射却又走 `@One` 嵌套 select —— JOIN 出来的列一个都没用上。
   本项目改成只查员工表（否则等于"JOIN 一遍 + 子查询再查一遍")。

## 三、写错映射的现场（探针实测，MyBatis 3.5.10）

| 写法 | 结果 |
|---|---|
| `<association property="deptInfo" javaType="Dept">` | 正常 |
| `<association property="deptInfo">`（省略 javaType） | 也正常 —— association 能靠 property 的 setter 类型反射出 Dept |
| `<collection property="emps">`（省略 ofType） | 崩：`NullPointerException: Cannot invoke "Object.hashCode()" because "key" is null` |
| `<collection ofType="java.util.List">` | 崩：`UnsupportedOperationException` |
| 单对象属性误写 `<collection>` | **不报错，静默丢数据**：`deptInfo` 保持 null |
| 集合属性误写 `<association javaType="Skill">` | 崩：`IllegalArgumentException: argument type mismatch` |
| `property="noSuchField"` | 崩：`ReflectionException: There is no getter for property named 'noSuchField'` |

这些错法在 **解析期全部通过**（`mybatis-3.5.10` 的 DTD 里 `collection` 的 `javaType`/`ofType` 都是 `#IMPLIED`），
一律推迟到查库那一刻才炸 —— 改完映射必须真跑一条查询，建得起 `SqlSessionFactory` 不代表写对了。
